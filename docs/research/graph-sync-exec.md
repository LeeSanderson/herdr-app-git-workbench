# Fetch, pull and push through Herdr's `exec()` on Windows

Research for #37 (part of #35). Date: 2026-11-25.
Environment checked: Windows 11, Git for Windows 2.45.2, Git Credential Manager (GCM) 2.5.0, Herdr Desktop with herdr-core (`hc`).

## Short answer

- `exec()` is a plain run-to-completion call. It has no stdin, no env vars, no streaming and no cancel. Its only knobs are `cwd`, `on` and `timeout` (default 30 s, max 600 s). It **rejects** on timeout, so any partial output is lost. Source: `~/.config/herdr-app/herdr.d.ts` line 10-14 and Herdr's `AGENTS.md` ("Machine: exec(...)").
- With no terminal, Git **does not hang** on a username/password prompt. It fails in about 1 s with exit 128. This held both through `hc exec` and from a console-less parent that gives git a hidden console. SSH host-key and key prompts also fail at once. So `GIT_TERMINAL_PROMPT=0` and `BatchMode=yes` are not needed to avoid hangs. They only make the error text cleaner.
- **GCM is the one real wait.** GCM shows its own GUI (browser OAuth or a dialog) without needing a terminal. While it is open, `exec()` stays blocked until the user finishes or the timeout ends. There is no way to cancel it from the mod. For a desktop app this is the behaviour we want, as long as sync uses the long timeout and the UI shows a "waiting for sign-in" state.
- `--progress` is useless here. `exec()` returns stderr only at the end, so progress lines just add bytes to stderr. Don't pass it. Show an indeterminate busy state.
- Every failure is a non-zero exit plus stable English text on stderr. The table below lists them. For push, `--porcelain` gives a machine-readable status line per ref on stdout.

## 1. What `exec()` supports

From the installed `herdr.d.ts` (generated by Herdr, authoritative):

```ts
/** Runs a program with the user's real environment (HOME, PATH, auth). 8 MiB output.
 *  `timeout`: milliseconds, defaults to 30,000, capped at 600,000 (10 minutes).
 *  `on`: on that machine (a space's `machine`) through herdr-core, its home by default.
 *  Rejects when it can't start (not installed, no such folder, the machine is unreachable). */
export function exec(command: string, args?: string[], options?: { cwd?: string; on?: string | null; timeout?: number }): Promise<ExecResult>;
// ExecResult = { code: number; stdout: string; stderr: string }
```

Herdr's `AGENTS.md` (in `~/.config/herdr-app/`) adds: "It rejects on timeout, if the program cannot start or the machine cannot be reached." It also says: "An `exec` already started keeps running" when a view closes.

| Capability | `exec()` | Notes |
|---|---|---|
| Env vars | No | Only "the user's real environment". |
| Stdin | No | `hc exec` without `-i` gives EOF on stdin. Seen with `set /p`, which read nothing. |
| Streaming / progress | No | One promise with the whole stdout and stderr, up to 8 MiB. |
| Cancel | No | No handle or signal. Closing a mod copy does not stop a running `exec`. |
| Timeout | Yes | 30 s default, 600 s cap. On timeout the promise **rejects**, so partial output is lost. `src/core/git.js` maps this to `GitTimeout` and already has `TIMEOUTS.long = 600_000`. |

`hc exec` (herdr-core CLI, `hc exec --help`) can do more: `--env K=V` (repeatable), `-i/--stdin`, and `--timeout` in seconds (default 60, max 600). On timeout it ends "it and everything it started". With `--json` it returns `{code, stdout(base64), stderr(base64), timed_out, truncated, ms}` and keeps partial output. Tested: `hc exec --json --timeout 3 -- bash -c "echo started; sleep 30"` gave `timed_out: true` with stdout `started`. So if the mod ever needs env vars, it can run `exec("hc", ["exec", "--json", "--env", "GIT_TERMINAL_PROMPT=0", "--cwd", cwd, "--", git, ...])`. Git for Windows' `usr/bin/env.exe GIT_TERMINAL_PROMPT=0 git ...` also works, but it is Windows-only and tied to an install path. Neither is needed for the cases below.

## 2. Prompts with no terminal

### HTTPS username/password

Git asks for credentials in this order: credential helper, then `GIT_ASKPASS`, then `core.askPass`, then `SSH_ASKPASS`, then the terminal ([gitcredentials](https://git-scm.com/docs/gitcredentials)). `GIT_TERMINAL_PROMPT=false` stops only the last step ([git](https://git-scm.com/docs/git)).

Seen through `hc exec`, with no helper (`-c credential.helper=`), against a GitHub URL that does not exist:

| Setup | Result |
|---|---|
| Prompts allowed (default) | exit 128 after about 1 s. `bash: line 1: /dev/tty: No such device or address` / `error: failed to execute prompt script (exit code 1)` / `fatal: could not read Username for 'https://github.com': No such file or directory` |
| `GIT_TERMINAL_PROMPT=0` | exit 128: `fatal: could not read Username for 'https://github.com': terminal prompts disabled` |
| `-c core.askPass=true` (askpass gives empty answers) | exit 128: `remote: Repository not found.` / `fatal: Authentication failed for '<url>/'` |

Git for Windows' terminal prompt runs a bash script that reads `/dev/tty`. With no console that read fails at once. I repeated the check from a console-less parent (Node, `detached: true`) that spawns git with `windowsHide: true`, so git gets a **hidden** console. That is the setup most likely to look like a GUI app. The result was the same fast failure, in 0.5 s. **Not verified:** the exact process flags Herdr's local `exec()` uses. The in-app check in section 6 closes this gap.

Note: Claude Code sets `GIT_TERMINAL_PROMPT=0` in its own shell. `hc exec` runs with herdr-core's environment, so the results above are not affected by it.

### Git Credential Manager (the configured helper: `credential.helper=manager` in the system gitconfig)

From [GCM environment docs](https://github.com/git-ecosystem/git-credential-manager/blob/main/docs/environment.md):

- `GCM_INTERACTIVE` / `credential.interactive`: "Permit or disable GCM from interacting with the user (showing GUI or TTY prompts)." If it is `false` or `never` and interaction is needed, "an error is returned". The default is enabled.
- `GCM_GUI_PROMPT` / `credential.guiPrompt`: turns GUI prompts on or off. When off, "If an equivalent terminal/ text-based prompt is available, that will be shown instead."
- `credential.gitHubAuthModes`: `browser` is "OAuth authentication via a web browser _(requires a GUI)_". `device` is a device-code flow.

So with the default settings, GCM shows a GUI window or opens a browser even though git has no terminal. `exec()` then blocks until the user finishes or the timeout ends. I did not trigger this, to avoid opening windows on the user's desktop. With `-c credential.interactive=false` (seen, gitlab.com, no stored credential):

```
fatal: Cannot prompt because user interactivity has been disabled.
fatal: could not read Username for 'https://gitlab.com': terminal prompts disabled   (with GIT_TERMINAL_PROMPT=0)
```

Without `GIT_TERMINAL_PROMPT=0`, the second line is the `/dev/tty` failure shown above. The exit code is 128 either way. `credential.interactive` can be set with `-c`, so it needs no env var. That gives a "silent background fetch" mode: `-c credential.interactive=false` for automatic or periodic fetches, and the default (GUI allowed) for fetches, pulls and pushes the user starts.

### SSH host key and passphrase

[`ssh_config`](https://man.openbsd.org/ssh_config): `BatchMode=yes` disables "password prompts and host key confirmation requests". `StrictHostKeyChecking=accept-new` adds new host keys but refuses changed ones. `ConnectTimeout` limits the connect and handshake time. [`ssh(1)`](https://man.openbsd.org/ssh): with no terminal, ssh uses `SSH_ASKPASS` only if `DISPLAY` and `SSH_ASKPASS` are set, or if `SSH_ASKPASS_REQUIRE=force`. In the herdr-core environment neither was set.

Git for Windows runs its own `/usr/bin/ssh` (`GIT_TRACE` shows `run_command: ... ssh -o SendEnv=GIT_PROTOCOL git@github.com ...`). Seen through `hc exec`:

| Setup | Result |
|---|---|
| Unknown host key, default ssh (no BatchMode) | exit 128 in about 1 s: `Host key verification failed.` then `fatal: Could not read from remote repository.` |
| Same with `BatchMode=yes` | Same text and exit code. |
| Known host, no usable key | exit 128: `git@github.com: Permission denied (publickey).` then the same `fatal:` block. |

With no terminal, the host-key question fails at once. A passphrase-protected key is not loaded into an agent, so it is skipped and the run ends in `Permission denied (publickey)`. I did not test that case directly, because no passphrase key was registered with a remote. Recommendation: **don't** force `core.sshCommand` / `GIT_SSH_COMMAND`. Both override the user's own SSH choice, such as Windows OpenSSH with its agent service, or plink/Pageant ([git-config core.sshCommand](https://git-scm.com/docs/git-config)). If a guard is wanted, append nothing. Instead, map the error texts above to "SSH authentication failed: check your key/agent or open a terminal". **Unverified:** a user `core.sshCommand` that points at Windows OpenSSH (`C:\Windows\System32\OpenSSH\ssh.exe`) may act differently on passphrase prompts when there is no console.

## 3. Progress output

[git-fetch](https://git-scm.com/docs/git-fetch) and [git-push](https://git-scm.com/docs/git-push), `--progress`: "Progress status is reported on the standard error stream by default when it is attached to a terminal ... This flag forces progress status even if the standard error stream is not directed to a terminal." Seen: without `--progress`, a fetch through `exec` writes only the `From <url>` and ref-update lines to stderr. With it, `remote: Enumerating objects ... Counting objects: 100% ...` is added, using `\r` to redraw lines. `exec()` cannot stream, so this text only arrives after the command ends. **Don't pass `--progress`.**

## 4. Exit codes and error text (seen, git 2.45.2, through `hc exec`)

Human-readable output goes to **stderr**. Merge and rebase conflict lines go to **stdout**.

| Case | Command | Exit | Key text (stream) |
|---|---|---|---|
| Fetch OK | `fetch origin` | 0 | stderr: `From <url>` / `   a..b  main -> origin/main` |
| Fetch, no remote configured | `fetch` | 0 | (nothing). This is not an error. |
| Fetch, remote path or repo missing | `fetch origin` | 128 | `fatal: '<url>' does not appear to be a git repository` / `fatal: Could not read from remote repository.` |
| Push OK, new branch | `push -u origin HEAD` | 0 | stderr: ` * [new branch]      HEAD -> feature`. stdout: `branch 'feature' set up to track 'origin/feature'.` |
| Push, nothing to do | `push` | 0 | stderr: `Everything up-to-date` |
| Push rejected, behind (already fetched) | `push` | 1 | ` ! [rejected]        main -> main (non-fast-forward)` / `error: failed to push some refs to '<url>'` / `hint: Updates were rejected because the tip of your current branch is behind` |
| Push rejected, remote has unfetched work | `push` | 1 | ` ! [rejected]        main -> main (fetch first)` / `hint: Updates were rejected because the remote contains work that you do not` |
| Push rejected, `--porcelain` | `push --porcelain origin main` | 1 | stdout: `To <url>` / `!\trefs/heads/main:refs/heads/main\t[rejected] (non-fast-forward)` / `Done`. stderr: `error: failed to push some refs ...` + hints |
| Push, no upstream | `push` | 128 | `fatal: The current branch feature has no upstream branch.` / `    git push --set-upstream origin feature` |
| Push, no remote at all | `push` | 128 | `fatal: No configured push destination.` |
| Pull, no upstream | `pull` | 1 | `There is no tracking information for the current branch.` |
| Pull, diverged, no `pull.rebase`/`pull.ff` set | `pull` | 128 | `hint: You have divergent branches and need to specify how to reconcile them.` / `fatal: Need to specify how to reconcile divergent branches.` |
| Pull, diverged, `--ff-only` | `pull --ff-only` | 128 | `fatal: Not possible to fast-forward, aborting.` |
| Pull, merge conflict | `pull` (merge) | 1 | stdout: `Auto-merging f.txt` / `CONFLICT (content): Merge conflict in f.txt` / `Automatic merge failed; fix conflicts and then commit the result.` |
| Pull, rebase conflict | `pull --rebase` | 1 | stdout: `CONFLICT (content): ...`. stderr: `error: could not apply 199277f... b1` / `hint: ... "git rebase --continue"` |
| Pull while conflicts are unresolved | `pull` | 128 | `error: Pulling is not possible because you have unmerged files.` / `fatal: Exiting because of an unresolved conflict.` |
| Pull, local changes would be overwritten | `pull` | 1 | `error: Your local changes to the following files would be overwritten by merge:` / `\tf.txt` / `Aborting` |
| HTTPS auth, no prompt possible | `ls-remote <https>` | 128 | `fatal: could not read Username for '<host>': ...` (see section 2) |
| HTTPS auth, bad credentials | | 128 | `fatal: Authentication failed for '<url>/'` |
| GCM non-interactive, needs prompt | | 128 | `fatal: Cannot prompt because user interactivity has been disabled.` |
| SSH | | 128 | `Host key verification failed.` or `Permission denied (publickey).`, then `fatal: Could not read from remote repository.` |
| Timeout | any | n/a | `exec()` rejects. `git.js` throws `GitTimeout`. |

Notes:

- **Exit codes don't tell failures apart.** Both 1 and 128 cover several cases. The git docs don't define exit codes for fetch or pull, and git-push only says "non-zero" ([git-push](https://git-scm.com/docs/git-push)). Classify by text: `CONFLICT (` on stdout, `[rejected]` and `(non-fast-forward)`/`(fetch first)`, `has no upstream branch`, `no tracking information`, `Need to specify how to reconcile`, `would be overwritten by`, `Authentication failed` / `could not read Username` / `Cannot prompt` / `Permission denied (publickey)` / `Host key verification failed`. Git messages can be localised, and `exec()` can't set `LC_ALL`/`LANG`, so an unmatched message must fall back to "show raw stderr".
- **For a conflict, read the state, not the text.** After pull exits non-zero, `.git/MERGE_HEAD` or `.git/rebase-merge/` (or `status --porcelain=v2` showing `u` entries) is the reliable signal. The existing status parser already covers unmerged entries.
- **The divergent-pull default depends on config.** Git for Windows' system gitconfig here sets `pull.rebase=false`, so a plain `pull` merged and then conflicted. With `GIT_CONFIG_NOSYSTEM=1` it failed with "Need to specify how to reconcile". The current online [git-pull](https://git-scm.com/docs/git-pull) page (a newer git than 2.45) describes `--ff-only` as the default. **The mod should always pass an explicit mode** (`--ff-only`, `--rebase` or `--no-rebase`) so the result doesn't depend on the user's git version or config.
- **No upstream:** offer `push -u origin HEAD` (or honour `push.autoSetupRemote`, [git-push](https://git-scm.com/docs/git-push)). Detect the case before running, from `status --porcelain=v2 --branch` (no `# branch.upstream` line), instead of parsing the error.

## 5. Recommendations for the Graph sync actions

1. Run fetch, pull and push with `timeoutClass: "long"` (600 s, the `exec()` cap). The UI shows "Syncing... (sign-in window may be open)" and cannot offer Cancel. Disable the buttons while a sync runs.
2. Add no env vars. Pass `-c credential.interactive=false` only for background or automatic fetches, so they never open GCM windows unasked. Fetches, pulls and pushes the user starts keep GCM's GUI.
3. Don't pass `--progress`. Use `push --porcelain` to get per-ref results. Optionally use `fetch --porcelain`, which is git 2.41 or later ([git-fetch](https://git-scm.com/docs/git-fetch)).
4. Always pass an explicit pull mode. After a non-zero pull, check repo state for merge or rebase in progress.
5. Map the stderr patterns in section 4 to short messages, and always keep the raw stderr behind a "details" toggle.
6. Don't override `core.sshCommand`. With no TTY, SSH already fails fast.

## 6. Gaps to check in the app

- Run one HTTPS `ls-remote` with `credential.helper=` through the **mod's** `exec()` (not `hc exec`). The aim is to confirm it also fails fast rather than blocking on a hidden console.
- Confirm whether `exec()` timeout kills git's child processes (`git-remote-https`, `ssh`, GCM). `hc exec` says it does. `herdr.d.ts` is silent.
- GCM GUI flow end to end: does the window appear in front of Herdr, and does the promise resolve after sign-in?
- A passphrase-protected key with Windows OpenSSH set as `core.sshCommand`.

## Reproduce

Throwaway scripts (not committed) built a bare remote plus two clones in a temp folder. They ran each command as `hc exec --cwd <clone> --timeout 30 -- git <args>` and recorded the exit code and both streams. Auth cases used a non-existent GitHub/GitLab repo, and `ssh://git@ssh.github.com:443/...` with `UserKnownHostsFile=/dev/null` for the unknown-host-key case. Nothing was pushed to a real remote.
