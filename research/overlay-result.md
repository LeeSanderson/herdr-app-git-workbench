# Getting a yes/no answer back from a dialog overlay

Research for issue #12 (map: #1). Herdr Desktop (herdr-app) 0.1.16.

**Question.** Discard needs a confirmation. `openOverlay` returns only an id, and the shipped
`confirm` mod only runs a command on "yes". How can a dialog send its result back to the mod
that opened it?

**Answer.** There are two clean ways. Neither needs the inline "Discard? Yes / No" fallback.

1. **Recommended: shipped `confirm` dialog + a mod command.** Open the shipped `confirm` mod.
   Give it `command: { name: "herdr-app-git-workbench.discard" }`. On "yes" it calls `run()`.
   `run("<mod>.<command>")` delivers `"discard"` to the panel's `nextCommand()` loop. The panel
   stores *what* to discard in its own instance state before it opens the dialog, because only the
   command string arrives.
2. **For a custom dialog: open an overlay of the same mod and share a module-scope promise.**
   Module code is shared by all copies of a mod, so the overlay copy can resolve a promise that
   the panel copy is awaiting. This gives a real `await confirm(...) -> boolean`, including "no".

`setShared` also works but is the wrong tool (see "Rejected" below).

All sources are local files that Herdr generates or ships:
`~/.config/herdr-app/herdr.d.ts` ("Generated by Herdr; do not edit"),
`~/.config/herdr-app/AGENTS.md` and `~/.config/herdr-app/mods/*`.
Line numbers are as of 0.1.16.

There is **no** event bus, message-passing API, `openOverlay(...).then(result)`, or
close-with-result in `herdr.d.ts`. The whole module is 481 lines and was read end to end.

## 2. How the shipped mods send results back

- **`confirm`** (`mods/confirm/main.js`). Props are `{ title, detail, command: { name, args } }`.
  On yes it calls `closeOverlay(p.overlay)` and then `run(p.command.name, p.command.args ?? {})`
  (main.js:15-18). Enter means yes. Esc and Cancel only close it (main.js:31, :49). **Result
  channel: a command, on yes only.**
- **`prompt`** (`mods/prompt/main.js`). The same pattern. It calls
  `run(p.command.name, { ...p.command.args, name: this.text })`, so the typed value travels
  as a command *argument*. That works for app commands such as `tab.rename`.
- **`menu`** (`mods/menu/main.js:110-117`). It closes itself, then calls `run(it[1], it[2])`, or opens
  another overlay (`worktree`). **Result channel: a command.**
- **`picker`** (`mods/picker/main.js`). It closes itself and calls `run("tab.select", ...)` etc.
  It uses `setShared` only for space colours, not for results.
- **`agents` opens an overlay of itself.** It calls
  `openOverlay({ mod: "agents", kind: "popup", ..., props: { sortMenu: true } })` (agents/main.js:438).
  The popup copy writes the choice with `setShared("agents.sort", s.id)` and then
  `closeOverlay(props().overlay)` (agents/main.js:157-159). The docked copy reads
  `shared("agents.sort")` when it renders. **Result channel: shared state.**
- **`win98`** opens many overlays of itself (`mod: "win98"` with different `props.role`), for
  example taskbar.js:186, dialog.js:239, sol.js:130. It coordinates through `setShared` and
  `nextCommand()` (taskbar.js:89-98).

So "a mod opens an overlay of itself with different props" is a shipped, supported pattern.
`mod.clone` even rewrites "self-opening overlay names" (AGENTS.md:206-207; herdr.d.ts:83).

## 3. The sub-questions

**Can one mod register a command another overlay can invoke?** Yes, implicitly. Nothing is
registered. Any `run("<mod>.<command>")`, from any mod and from keys.json, delivers the
`<command>` string to `nextCommand()` in every *shown* copy of `<mod>` (herdr.d.ts:89;
AGENTS.md:528, :901). There are limits:
- `nextCommand()` resolves to a `string` only (herdr.d.ts:458). Nothing documents a way to read
  the `args` given to `run` for a mod command. Assume they are dropped.
- It goes to *shown* copies only. A docked panel that is shown qualifies.
- It goes to **every** shown copy of the mod, including an open overlay copy of the same mod.
  Make it idempotent, or check that the copy has a pending request.
- A mod with `"focusable": true` also receives `"focus"` through the same loop
  (AGENTS.md:882-885). Ignore unknown commands.

**Can a mod open an overlay of itself and share module state?** Yes. Copies share the module
(AGENTS.md:978-980), so a module-level `Map` is visible to both the panel and its overlay.
Instance fields (`this.*`), tasks and localStorage are per copy. Caveat: saving a source file
reloads every copy with a *new* module (AGENTS.md:890-895). A pending request across a hot-reload
is lost, and that only matters during development.

## 4. Recommendation A: the shipped `confirm` + `nextCommand()` (no new dialog code)

This reuses Herdr's own dialog, so the look, Enter/Esc handling, theming and "modal" behaviour
come for free.

```js
// mods/herdr-app-git-workbench/main.js
import { View } from "gpui-kit";
import { openOverlay, nextCommand, exec } from "herdr";

const MOD = "herdr-app-git-workbench";

export default class Workbench extends View {
  init(_props, cx) {
    this.pendingDiscard = null;            // per-copy; only the string comes back
    cx.spawn(async (cx) => {
      for (;;) {
        const c = await nextCommand();
        if (c === "discard" && this.pendingDiscard) {
          const { repo, path } = this.pendingDiscard;
          this.pendingDiscard = null;
          await exec("git", ["restore", "--worktree", "--", path], { cwd: repo });
          this.reload?.();
        }
        cx.notify();
      }
    });
  }

  askDiscard(repo, path) {
    this.pendingDiscard = { repo, path };
    openOverlay({
      mod: "confirm", kind: "dialog", modal: true, width: 420, height: 170,
      props: {
        title: "Discard changes?",
        detail: `${path} will be restored to the last commit. This cannot be undone.`,
        command: { name: `${MOD}.discard` },   // args would not reach nextCommand()
      },
    });
  }
}
```

Points to note:
- "No" or Esc sends nothing, and `pendingDiscard` stays set. Clear it on the next `askDiscard`,
  or when the file list changes, so that a later stray `discard` cannot hit a stale file. To make
  this safer, give each request a token and check it (for example, keep `{token, repo, path}` and
  compare a `shared` nonce). The simpler rule ("only act if pending is set, then clear it") is
  usually enough.
- If the user shows two copies of the panel, both receive `"discard"`. Only the copy that set
  `pendingDiscard` acts on it.
- The confirm button label is fixed to "Confirm" (confirm/main.js:50). If "Discard" or a danger
  colour is wanted, use option B.
- `mod.clone` rewrites self-opening overlay names. It is not documented to rewrite command strings,
  so a cloned copy would still send `herdr-app-git-workbench.discard`. Build the name from a constant
  and accept this limit.

## 5. Recommendation B: a self-overlay with a module-scope promise (a true boolean)

Use this when a custom dialog is wanted (for example a "Discard" button in danger colour, a list
of files, or "don't ask again"), or when the panel needs `false` back as well.

```js
import { View } from "gpui-kit";
import { openOverlay, closeOverlay, props } from "herdr";

const MOD = "herdr-app-git-workbench";
const pending = new Map();                 // module scope: shared by every copy
let seq = 0;

export function confirmDialog(spec) {      // call from the panel copy
  const req = `c${++seq}`;
  return new Promise((resolve) => {
    pending.set(req, resolve);
    openOverlay({ mod: MOD, kind: "dialog", modal: true, width: 420, height: 180,
                  props: { role: "confirm", req, ...spec } });
  });
}

function answer(value) {                   // call from the overlay copy
  const p = props();
  pending.get(p.req)?.(value);
  pending.delete(p.req);
  closeOverlay(p.overlay);
}

export default class Workbench extends View {
  // Esc or a click outside closes the overlay without a button: report "no".
  async close() { if (props()?.role === "confirm") answer(false); }

  render(cx) {
    if (props()?.role === "confirm") return this.renderConfirm(cx); // Yes -> answer(true), No -> answer(false)
    return this.renderPanel(cx);
  }

  async onDiscardClicked(repo, path, cx) {          // panel side; called inside cx.spawn
    if (await confirmDialog({ title: "Discard changes?", detail: path })) {
      /* exec git restore ... */
    }
  }
}
```

Notes:
- The panel awaits the promise inside a `cx.spawn(async (cx) => ...)`, so it has a live `cx` and
  can `cx.notify()` after it resumes. Do not keep a stale `cx` (AGENTS.md:981-983).
- `close(cx)` runs when the overlay goes, including by Esc (AGENTS.md:990-991). The answer must be
  idempotent because `answer(true)` also closes the overlay. `pending.delete` handles that: the
  second call finds no resolver.
- AGENTS.md:979 advises keeping *instance* state out of module scope. A small request→resolver
  registry is coordination state that is meant to be shared, which is exactly the case
  "shared by copies" describes. It is lost on hot-reload (development only).

## 6. Rejected options

- **`setShared` as the result channel** (the `agents` sort popup pattern). It works, but values
  are *persisted* (`shared.json`, herdr.d.ts:445) and every set "re-renders all" mods
  (AGENTS.md:1136-1137). That suits preferences, but it is noisy for a one-off answer. A stale
  "yes" could also survive a restart unless it is cleared.
- **`notify({action})`.** This is a toast, not a modal question.
- **Inline "Discard? Yes / No" in the file row.** This is still possible but not needed. Keep it
  only if a dialog is judged too heavy for single-file discards.

## 7. Not verified at runtime

No test mod was installed (the task forbids changes under `~/.config/herdr-app`). These points
rest on the documentation above and should be checked during the first build:
- `run("<mod>.<command>")` called from *another mod* (`confirm`) reaches our panel's
  `nextCommand()`. herdr.d.ts:89 documents it under `run`. The shipped mods only demonstrate it
  from keys.json.
- `args` passed with a mod command are dropped. This is inferred from `nextCommand(): Promise<string>`.
- A module-level `Map` is the same object in a docked copy and in an overlay copy of the same
  mod. This is stated by AGENTS.md:978 but not demonstrated by a shipped mod.
